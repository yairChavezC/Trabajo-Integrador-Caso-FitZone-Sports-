# ADR-006: Framework frontend, librería de componentes y gestión de estado global

**Estado:** Aprobado  
**Fecha:** 2026-09-15  
**Autor:** Equipo FitZone Sports  
**Sprint:** 2 (Unidad IV)  

## Contexto
FitZone Sports requiere una aplicación web accesible tanto desde dispositivos móviles para los socios (visualización de QR dinámico, gestión de membresías, reserva de canchas, inscripción a clases y pagos) como desde computadoras de escritorio en las 25 sedes para recepcionistas y gerentes (control de acceso con soporte offline, administración de turnos y facturación). En el marco de la Unidad IV, se necesita definir el framework frontend, la estrategia de componentes visuales y el mecanismo de gestión de estado global manteniendo coherencia con la arquitectura modular del proyecto.

## Decisión
Se adopta **React con Vite** como Single Page Application (SPA), acompañado por:
- **Componentes visuales:** Componentes funcionales reutilizables propios organizados en `shared/components/` y layouts diferenciados por rol (`AdminLayout`, `MemberLayout`, `AuthLayout`), apoyados en estilos CSS modulares/responsivos y utilidades livianas de interfaz (iconografía/QR) sin acoplar el dominio a una suite pesada.
- **Gestión de estado global:** **React Context API + hooks personalizados** (como `AuthContext`, `useAuth` y `usePermissions`) para administrar el estado transversal de sesión JWT, control de acceso basado en roles (RBAC) y estado de conectividad/sincronización, manteniendo el estado local y de datos de negocio encapsulado dentro de cada módulo (`modules/`) y su capa de servicios (`services/`).

## Consecuencias
**Positivas:**
- [+] Compilación ultrarrápida con Vite y experiencia fluida tipo SPA tanto en el portal móvil del socio como en la consola de recepción.
- [+] Separación limpia entre estado global transversal (autenticación y permisos RBAC) y estado local de cada dominio funcional.
- [+] Control total sobre el diseño y comportamiento de los componentes reutilizables sin sobrecarga de dependencias externas pesadas.

**Negativas:**
- [-] Requiere mantener orden en la granularidad de los contextos de React para evitar re-renderizados innecesarios en vistas complejas.
- [-] Exige disciplina del equipo para reutilizar los componentes base de `shared/` y mantener consistencia visual entre los distintos módulos.

**Deuda asumida:**
- [-] Si la aplicación incorpora mayor volumen de datos cacheados o sincronización en tiempo real entre múltiples vistas simultáneas, evaluar la incorporación de una librería dedicada de estado servidor/caché en futuras iteraciones.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| Next.js (SSR / Full-stack React) | Renderizado del lado del servidor y enrutamiento basado en archivos integrado. | Agrega complejidad operativa y de servidor innecesaria cuando ya existe una API REST independiente en Express y se requiere operación offline en cliente (ADR-003). | Descartada por priorizar una SPA cliente desacoplada y compatible con la contingencia offline en navegador. |
| Angular | Framework completo con inyección de dependencias, formularios y estructura rígida incluidos. | Curva de aprendizaje más pronunciada y mayor verbosidad para el ritmo de entrega del equipo en el cuatrimestre. | Descartada frente a React + Vite por velocidad de desarrollo y flexibilidad. |
| Redux Toolkit + librería UI pesada (ej. Material UI) | Gestión de estado centralizada muy predecible y catálogo extenso de widgets listos para usar. | Mayor *boilerplate* para un estado global acotado (sesión/RBAC) y mayor peso de *bundle* / personalización visual más rígida. | Descartada por resultar excesiva para las necesidades de estado global del proyecto y preferir una interfaz limpia y liviana. |
