# ADR-016 — Control de acceso por roles y sede

- **Estado:** Aceptado
- **Fecha:** 2026-11-16
- **Autor:** Acosta, Marcela
- **Sprint:** 4
- **Requisitos relacionados:** RF-03, RN-01

## Contexto

El sistema tiene 4 roles (socio, recepcionista, gerente, cliente_externo). Cada rol tiene permisos distintos sobre las clases grupales. Además, un recepcionista solo puede gestionar la sede que tiene asignada (`usuario_sede`).

## Alternativas consideradas

| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| Sin control (todos pueden todo) | Simple | Inseguro | Descartada |
| Control en frontend | UX | Inseguro (backend no confía) | Complementaria |
| Middleware de autorización en backend | Seguro, centralizado | Requiere pasar idSede por JWT o lookup | **Adoptada** |
| Control en cada controlador | Granular | Repetitivo | Descartada |

## Decisión

- `verificarToken` middleware decodifica JWT y setea `req.usuario = { id, rol }`.
- `requireRoles(rolesPermitidos)` middleware rechaza si el rol no está en la lista.
- `createRequireAgendaManager` verifica que el recepcionista solo acceda a su `idSede`.
- `getCurrentUserRole` consulta el tipo de rol desde la BD.

## Consecuencias

- **Positivas:** Control centralizado, fácil de auditar.
- **Negativas:** Cada request hace un lookup a BD para el rol (cacheable).
- **Deuda asumida:** Cachear roles en memoria para reducir queries.
