# ADR-005: Framework backend, inversión de control y persistencia

**Estado:** Aprobado  
**Fecha:** 2026-09-08  
**Autor:** Equipo FitZone Sports  
**Sprint:** 2 (Unidad II)  

## Contexto
Definido el estilo de monolito modular con separación por capas (controlador, servicio, repositorio) en el ADR-001 y PostgreSQL/Supabase como base de datos relacional en el ADR-002, el equipo necesita establecer las herramientas de aplicación del backend para la Unidad II: el framework HTTP, la forma de gestionar la inversión de control/dependencias entre capas y el mecanismo de persistencia de datos. Se busca mantener un stack ágil en JavaScript/Node.js, con control explícito de las transacciones y consultas SQL y facilidad para testear la lógica de negocio.

## Decisión
Se adopta **Node.js con Express** como framework backend para exponer los endpoints REST de cada módulo, **inyección/composición explícita de dependencias** (inyectando repositorios, servicios y adaptadores al instanciar cada módulo/servicio sin depender de un contenedor IoC automático pesado) y **repositorios con acceso directo a PostgreSQL mediante SQL parametrizado** (sin ORM pesado, encapsulando el acceso a datos en la capa de repositorio de cada módulo).

## Consecuencias
**Positivas:**
- [+] Stack homogéneo en JavaScript/Node.js, con curva de aprendizaje rápida y control directo sobre middlewares, rutas y manejo de errores en Express.
- [+] La inyección explícita de dependencias facilita sustituir repositorios reales por dobles/mocks en pruebas unitarias y de integración.
- [+] El acceso directo a PostgreSQL desde los repositorios mantiene visibilidad y control sobre transacciones, bloqueos (`SELECT ... FOR UPDATE`) y consultas relacionales.

**Negativas:**
- [-] Al no usar un contenedor IoC automático ni un ORM completo, el cableado de dependencias y el mapeo de entidades/consultas deben mantenerse ordenados y consistentes en cada módulo.
- [-] Exige disciplina del equipo para validar entradas y mantener separadas las responsabilidades entre controladores, servicios y repositorios.

**Deuda asumida:**
- [-] Estandarizar los DTOs, esquemas de validación y contratos entre módulos a medida que se incorporan nuevas funcionalidades y pruebas automatizadas.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| NestJS + TypeORM | Contenedor IoC nativo, arquitectura opinada por módulos y ORM integrado. | Mayor curva de aprendizaje, uso de decoradores/TypeScript y sobrecarga de configuración para el alcance del equipo. | Descartada por priorizar simplicidad operativa y control directo sobre Express y las consultas SQL. |
| Express + Prisma ORM | Tipado cómodo y definición declarativa de esquema y migraciones. | Capa de abstracción adicional que agrega complejidad y puede ocultar detalles de consultas/transacciones específicas de PostgreSQL. | Descartada para mantener acceso directo y transparente a PostgreSQL desde los repositorios. |
| Fastify | Buen rendimiento HTTP y validación de esquemas integrada. | Menor familiaridad del equipo y menor alineación directa con la base ya planteada en Express. | Descartada frente a Express por simplicidad de integración y ritmo de desarrollo del equipo. |
