# ADR-011 — Cancelación tardía con penalización en el módulo M3 Clases Grupales

- **Estado:** Aceptado
- **Fecha:** 2026-11-16
- **Autor:** Acosta, Marcela
- **Sprint:** 4
- **Requisitos relacionados:** RF-07, RN-03

## Contexto

El módulo M3 de Clases Grupales permite a los socios cancelar reservas de clases grupales. Sin embargo, si un socio cancela con menos de 2 horas de antelación al inicio de la clase (pero antes de que comience), se considera una "cancelación tardía". Se necesitaba desincentivar este comportamiento impidiendo que el socio con cancelaciones tardías recientes pueda reservar nuevas clases, unirse a listas de espera ni aceptar ofertas temporales durante un período de penalización.

## Alternativas consideradas

| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| No penalizar cancelaciones tardías | Simples de implementar, sin fricción para el usuario | Fomenta cancelaciones de último minuto, deja cupos sin ocupar y perjudica a otros socios | No cumple RF-07 (cancelaciones con y sin penalidad) |
| Bloqueo permanente tras una cancelación tardía | Fácil de implementar, disuasorio fuerte | Excesivamente punitivo, no permite que el usuario se redima | Descartado por ser desproporcionado |
| Bloqueo temporal de N horas tras cancelación tardía | Equilibrado, disuasorio pero permite redención, configurable | Requiere registrar fecha de cancelación y consultarla en cada reserva/lista de espera/oferta | Se adoptó como solución equilibrada |
| Bloqueo solo para reservas, permitir lista de espera y ofertas | Menos fricción para el usuario | Inconsistente: el usuario podría seguir ocupando cupos vía lista de espera | Descartado por inconsistencia de negocio |

## Decisión

Se implementó un bloqueo temporal de `PENALIDAD_CANCELACION_TARDIA_HORAS` horas (default 48) para usuarios con una cancelación `cancelado_tarde` reciente. El bloqueo se aplica en tres puntos: `reserveClass`, `joinWaitlist` y `acceptWaitlistOfferForUser`. La columna `fecha_cancelacion` se registra al cancelar y se consulta mediante `findUltimaCancelacionTardía` para calcular el fin del bloqueo.

## Consecuencias

- **Positivas:** Desincentiva cancelaciones de último minuto, protege los cupos de otros socios, configurable vía variable de entorno.
- **Negativas:** Requiere migración de base de datos (columna `fecha_cancelacion`, CHECK constraint con `cancelado_tarde`, índice parcial). Añade una consulta adicional por cada operación de inscripción.
- **Deuda asumida:** Si se necesita un panel de gestión de penalidades para recepcionistas/gerentes, se deberá agregar un endpoint de consulta y posiblemente un mecanismo de desbloqueo administrativo.
