# ADR-015 — Separación de servicios: activityService, inscriptionService y membershipRepository

- **Estado:** Aceptado
- **Fecha:** 2026-11-16
- **Autor:** Acosta, Marcela
- **Sprint:** 4
- **Requisitos relacionados:** RF-06, RF-07, RF-08

## Contexto

Inicialmente, toda la lógica estaba en `activityService`. Al agregar reservas, cancelaciones y lista de espera, el servicio se volvió demasiado grande y mezclaba responsabilidades.

## Alternativas consideradas

| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| Un solo servicio gordo | Menos archivos | Acoplamiento, difícil de testear | Descartada |
| activityService + inscriptionService | Separación clara de responsabilidades | Dos servicios coordinados | **Adoptada** |
| Un servicio por entidad (Activity, Inscription, Membership) | Máxima separación | Sobreingeniería para el alcance | Descartada |

## Decisión

- `activityService`: CRUD de clases grupales, control por rol/sede.
- `inscriptionService`: reservas, cancelaciones, lista de espera, ofertas, penalidad.
- `membershipRepository`: verificación de membresía activa (separado para no acoplar inscripciones a usuarios).

## Consecuencias

- **Positivas:** Cada servicio tiene una responsabilidad clara. Fácil de testear por separado.
- **Negativas:** Dos servicios que se llaman entre sí (activityService orquesta inscriptionService para cancelaciones).
- **Deuda asumida:** Si crece más, considerar CQRS o eventos.
