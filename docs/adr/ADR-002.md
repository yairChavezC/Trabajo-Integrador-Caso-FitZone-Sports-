# ADR-002: Motor de BD relacional

**Estado:** Aprobado  
**Fecha:** 2026-08-31  
**Autor:** Equipo FitZone Sports  
**Sprint:** 1 (Unidad I)  

## Contexto
FitZone Sports necesita almacenar y gestionar información relacionada con usuarios, membresías, pagos, clases grupales, inscripciones, canchas, reservas y sedes.
El sistema presenta operaciones que requieren mantener la consistencia e integridad de los datos (RNF-03). Entre ellas se encuentra la gestión de reservas, donde no debe ser posible que dos usuarios obtengan la misma disponibilidad, y las operaciones relacionadas con pagos.
Además, la solución debe permitir trabajar con un modelo de datos estructurado, mantener relaciones entre las distintas entidades y acompañar la evolución del proyecto mediante cambios controlados en el esquema de datos.

## Decisión
Vamos a utilizar **PostgreSQL** como motor de base de datos relacional y **Supabase** como entorno para su gestión. Se elige PostgreSQL por su estricto cumplimiento de propiedades **ACID**, integridad referencial mediante claves foráneas y restricciones únicas, y soporte robusto de transacciones y bloqueos a nivel de fila para operaciones críticas de reservas y pagos (RNF-03).

## Consecuencias
**Positivas:**
- [+] Permite trabajar con un modelo de datos relacional y estructurado.
- [+] Proporciona soporte para transacciones y consistencia de los datos.
- [+] Facilita la gestión de relaciones entre las entidades del sistema.
- [+] Permite realizar migraciones controladas durante la evolución del proyecto.
- [+] Supabase simplifica la gestión del entorno de PostgreSQL.
- [+] Monitoreo de recursos y métricas de rendimiento listas para usar.

**Negativas:**
- [-] El equipo deberá mantener correctamente el diseño y las relaciones del esquema de base de datos.
- [-] El proyecto queda condicionado a las herramientas y configuración del entorno seleccionado.
- [-] Será necesario definir y mantener las migraciones y restricciones de la base de datos a medida que avance el desarrollo.

**Deuda asumida:**
- [-] Mantener sincronizadas las migraciones SQL y restricciones de integridad entre los entornos de desarrollo/pruebas locales y la instancia administrada en Supabase.

## Alternativas consideradas
| Alternativa | A favor | En contra | Por qué se descartó |
|---|---|---|---|
| PostgreSQL autogestionado | Control total sobre la instalación y configuración del motor. | Implica que el equipo asuma directamente una mayor parte de la configuración y administración del entorno. | Se descartó para este proyecto porque implicaría que el equipo asuma directamente una mayor parte de la configuración y administración del entorno. |
| MySQL | Motor relacional ampliamente utilizado y de bajo costo operativo. | Carece del ecosistema integrado que ofrece Supabase (como autenticación, APIs automáticas y políticas de seguridad a nivel de fila). | Se descartó porque carece del ecosistema integrado que ofrece Supabase, lo que obligaría a desarrollar o integrar soluciones externas adicionales. |
| Base de datos NoSQL | Flexibilidad de esquema para documentos o datos no estructurados. | No garantiza de forma nativa la integridad referencial ni transacciones complejas entre múltiples entidades relacionadas. | Se descartó porque el sistema posee múltiples entidades relacionadas y requiere consistencia en operaciones como reservas y pagos, por lo que el modelo relacional resulta más adecuado para las necesidades identificadas. |
